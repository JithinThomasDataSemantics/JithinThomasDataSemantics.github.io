01 · Why bother

Built-in tools get you knowledge. Custom tools get you action.

Foundry Agent Service ships with built-in tools for gathering knowledge and generating code. But an AI model, on its own, can't check a real order, look up real inventory, or book a real appointment. A custom tool — your own code, or a third-party API — closes that gap.

🏬

The retail scenario this module is built around

A retail company's support team is drowning in repetitive order-status questions, and response times are slipping. Instead of hiring more agents, they build a custom FAQ agent equipped with a tool that looks up customer orders directly — freeing the human team to handle the complex cases.

⚙

Enhanced productivity

Automate repetitive tasks and streamline workflows that are specific to your use case — the agent handles the routine so people don't have to.

🎯

Improved accuracy

Tools provide precise, consistent outputs pulled straight from your systems, reducing the likelihood of human error in the response.

🧩

Tailored solutions

Address specific business needs and optimize processes that a generic, out-of-the-box agent simply can't reach.

Custom function (function calling)

Function calling lets you describe the structure of custom functions to an agent, which then returns the functions that need to be called along with their arguments. The agent dynamically identifies the appropriate function based on its definition. Useful for integrating custom logic and workflows, in a selection of programming languages, directly into your AI agents.

05 · Hands-on

The same snowfall tool, built three ways.

The module walks through one running example — checking recent snowfall for a location — implemented as a custom function, an Azure Function, and an OpenAPI tool. Switch tabs to compare the code side by side.

import json

def recent_snowfall(location: str) -> str:
    """
    Fetches recent snowfall totals for a given location.
    :param location: The city name.
    :return: Snowfall details as a JSON string.
    """
    mock_snow_data = {"Seattle": "0 inches", "Denver": "2 inches"}
    snow = mock_snow_data.get(location, "Data not available.")
    return json.dumps({"location": location, "snowfall": snow})

# Define a function tool for the model to use
function_tool = FunctionTool(
    name="recent_snowfall",
    parameters={
        "type": "object",
        "properties": {
            "location": {"type": "string", "description": "The city name to check snowfall for."},
        },
        "required": ["location"],
        "additionalProperties": False
    },
    description="Get recent snowfall totals for a given location.",
    strict=True,
)

# Add the function tool to a list of tools for the agent
tools: list[Tool] = [function_tool]

# Create your agent with the toolset
agent = project_client.agents.create_version(
    name="snowfall-agent",
    definition=PromptAgentDefinition(
        model="gpt-4.1",
        instructions="You are a weather assistant tracking snowfall. Use the provided functions to answer questions.",
        tools=tools,
    )
)
function.py — define the logic, then register it as a FunctionTool

Tip — OpenAPI authentication types

Three authentication types are supported with OpenAPI 3.0 tools: anonymous, API key, and managed identity. Choose based on how the target API expects to be called.

06 · The idea people trip on

You never write the code that calls your tool.

This is the single most common point of confusion for developers new to agent tools — worth slowing down for.

✓

The declarative nature of agent tools

You don't explicitly call your custom tool functions anywhere in your code. The agent itself decides to invoke a tool, based on the messages in the conversation. Give the agent functions with meaningful names and well-documented parameters, and it figures out — entirely on its own — when and how to call them.

What you might expect (imperative)

"I write code that says: if the user asks about weather, call recent_snowfall()." This is how traditional programs work — but it's not how agent tools work.

What actually happens (declarative)

You describe the tool's name, purpose, and parameters. The model reads the user's message, decides for itself that the tool is relevant, and generates the call — no branching logic required from you.
